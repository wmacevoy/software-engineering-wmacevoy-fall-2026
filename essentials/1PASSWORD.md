# Essentials: 1Password

You now own secrets: an SSH private key, two-factor recovery codes, and — the first time a project
talks to any service — an API key. A secret has one property that nothing else you handle has: once
it is in the wrong place, you cannot get it back. This is the tool that keeps secrets out of files,
out of chat, and out of the repository, while still getting them into the programs that need them.

- **The fear it retires:** "A secret is in the repo." And: "I'm locked out of the account with all
  my work in it."
- **The fence you prove:** `parking/` runs with `JWT_SECRET` injected by `op run`, nothing secret in
  any file, and your GitHub recovery codes are in the vault.
- **Before this:** `GIT.md`
- **After this:** `GITHUB-ISSUES.md`

Why this product: its developer tooling can put a secret into a program's environment at run time
so that it never touches a file, it has an SSH agent, and it has not lost its customers' vaults. Do
not use LastPass; its customer vaults themselves were stolen in the 2022 breach. Any manager with
the first two properties will do; the habits below are the point.

## The model

```
  vault ── items ── fields            the app (unlock with one password + a secret key)
    │                                  the browser extension (fills logins; generates passwords)
    │                                  the CLI, `op` (reads fields into a shell or a process)
    │                                  the SSH agent (signs with keys that never leave the vault)
    ▼
  repository: NO secrets.
  a template file: JWT_SECRET=op://Development/parking/jwt-secret     ← a reference, not a value
    │
    └── op run --env-file=.env.template -- npm start   ──▶  the process sees JWT_SECRET=<value>
                                                             and nothing on disk ever did
```

Three ideas:

- **A secret is a value that lives in exactly one place**, the vault, and is *referenced* everywhere
  else. A reference like `op://vault/item/field` is safe to commit; it is an address, not a key.
- **The environment is the delivery route.** Programs read secrets from environment variables
  (`SHELL.md`); the manager sets them for one process and nothing else sees them.
- **Your email account is the master key to everything else**, because every "forgot password"
  flow goes through it. It gets the strongest password, hardware or app two-factor, and its own
  recovery codes in the vault.

## Once per machine

1. **Install the app and the browser extension.** Create the account with a long master password
   you will actually type, and save the *Emergency Kit* — the PDF with your secret key — somewhere
   that is not this machine. Without the secret key, a new device cannot join, and support cannot
   help you.
2. **Install the CLI** (`op`), and turn on *Settings → Developer → Integrate with 1Password CLI* so
   that `op` unlocks with the app instead of asking for the password every time.
   `op signin` once, then `op whoami` to confirm.
3. **Turn on the SSH agent** (*Settings → Developer → Use the SSH agent*) and either import the key
   you made in `GIT.md` into the vault as an *SSH Key* item, or generate a new one there and add
   its public half to GitHub. Then tell SSH to ask the agent:

   ```
   # ~/.ssh/config
   Host *
     IdentityAgent "~/Library/Group Containers/2BUA8C4S2C.com.1password/t/agent.sock"   # mac
   # linux: IdentityAgent ~/.1password/agent.sock
   ```

   `ssh-add -l` should now list the key, and `ssh -T git@github.com` should still greet you. On
   Windows the agent speaks through the OpenSSH named pipe, and using it from WSL takes a bridge;
   if that is friction, keep the key file in WSL and store a *copy* of the key in the vault as the
   backup it should have anyway.
4. **Move your existing secrets in.** GitHub login and its two-factor recovery codes. Your email
   account and its codes. The SSH key. Anything currently in a notes file, a text message, or a
   screenshot of a QR code.

## Once per repository

1. **`.env` is in `.gitignore`.** Check before anything else. `git status` must never show it.
2. **Commit a template, not a value.** `.env.template` (or `.env.example`) holds references:

   ```
   DATABASE_URL=postgres://parking_user:parking_pass@localhost:5432/parking
   JWT_SECRET=op://Development/parking/jwt-secret
   ```

   The database line is not a secret here — it is the local Docker demo, and `docker-compose.yml`
   says so in plain text. The JWT secret is. That distinction is a decision; make it on purpose and
   write it down.
3. **Create the item.** In the *Development* vault, an item named `parking` with a field
   `jwt-secret`, generated by the app, long, never typed by a human.
4. **Run through the manager.**

   ```sh
   cd parking/app
   op run --env-file=../.env.template -- npm start
   ```

   `op` resolves every `op://` reference, sets the variables for that one process, and forgets
   them when it exits. `op read "op://Development/parking/jwt-secret"` prints one value when you
   need to see it, which should be rare.
5. **Share by vault, not by message.** A teammate who needs the secret gets access to the shared
   vault. A secret pasted into chat is in that chat's history forever, on servers you do not
   control.

## Every day

- The extension fills logins and generates a new password for every new site. You should not know
  any of your passwords except the master one.
- *Watchtower* tells you which saved passwords have appeared in a breach; rotate those.
- When a project needs a new key: generate it in the service, paste it into a vault item **once**,
  reference it from the template, close the tab. It never goes in a file.
- When a secret must be rotated — a teammate leaves, a laptop is lost — change the vault item and
  every process picks it up on its next start. That is the payoff for never copying it anywhere.

## Danger Will Robinson

- **A secret that was pushed is compromised**, however briefly it was there. Rotate it first —
  revoke, reissue — then, if you must, scrub history with `git filter-repo`, knowing that forks and
  caches may still have it.
- **`.env` in the repository.** The single most common way a key leaks. The `.gitignore` line is
  not optional, and `git add .` is how it gets bypassed (`GIT.md`).
- **Secrets in a Docker image.** `ENV JWT_SECRET=…` in a Dockerfile, or a build argument, is in
  the image's layers forever, and anyone who can pull the image can read it (`DOCKER.md`).
- **Secrets in a prompt.** Pasting a key into a chat with an agent sends it to a third party
  (`AGENT.md`).
- **Secrets in logs.** `L-7` in `parking/REQUIREMENTS.md`: credentials, private keys, and tokens are
  never logged; fingerprints and subjects are.
- **One password reused.** The breach of a site you forgot about becomes the breach of your email,
  and your email is the master key.

## When it goes wrong

| Symptom                                       | Cause                                          | Do                                                          |
| --------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------- |
| a key or token is in a commit                 | added by wildcard, or `.env` not ignored       | rotate it now; then clean history; then fix `.gitignore`    |
| `ssh -T` stopped greeting you after enabling the agent | SSH is asking the wrong agent         | `ssh-add -l`; check `IdentityAgent` in `~/.ssh/config`; `echo $SSH_AUTH_SOCK` |
| `op run` says it cannot resolve a reference   | vault, item, or field name is wrong            | `op item get parking --vault Development` and read the field names |
| locked out of GitHub after a phone change     | two-factor with no recovery codes              | the codes are in the vault — that is why they are there; if not, GitHub's recovery process is slow and may fail |
| a new laptop cannot unlock the vault          | no secret key                                  | the Emergency Kit; this is the one thing you cannot reset   |

## Checklist

- [ ] The Emergency Kit is stored somewhere that is not this machine.
- [ ] GitHub login, two-factor recovery codes, and the email account are items in the vault.
- [ ] `ssh-add -l` lists a key served by the agent, or the key file is backed up in the vault.
- [ ] `.env` is in `.gitignore`; `.env.template` with `op://` references is committed.
- [ ] `parking/` starts with `op run`, and no secret value is in any file in the repository.
- [ ] You know the rotate-first rule and could say it from memory.

## In `parking/`

`I-7` says no credential, private key, or signing key is committed or baked into an image; public
keys and trust anchors may be. `I-2` says a device's private key is generated on the device and never
leaves it — the same one-place rule, applied to a sensor. `L-7` keeps secrets out of logs. And
`app/index.js` falls back to `dev-secret` when `JWT_SECRET` is unset, with a warning: a deliberate
falsehood for a demo, and exactly the kind of default that reaches production when nobody has set up
the route this document describes.
